# skill-ci-controller

Helm chart for the skill-ci controller: it receives Harbor `PUSH_ARTIFACT` webhooks, creates one
`SkillEval` per skill digest and model, runs a runner Job for each, and moves the `beta` and
`stable` tags in Harbor according to the lift policy (see `CONTRACT.md` in the repository root).

The chart replaces `kubectl apply -k config/`. Its defaults reproduce `config/manager/deployment.yaml`.

## Requirements

- Helm 4 (tested with v4.3.0). The chart is `apiVersion: v2`, so Helm 3 can install it too.
- Kubernetes 1.27 or newer.
- Created out of band, in the release namespace (the chart creates none of them by default):
  - Secret `harbor-credentials` (`username`, `password`)
  - Secret `harbor-webhook` (`token`, optional)
  - Secret `llm-keys` (`anthropic`, optional `openai`), read by runner Jobs
  - Secret `docr` (image pull and task image push)
  - ConfigMap `skill-ci-models` (key `models.yaml`)
- Optional: the Prometheus Operator CRDs for `serviceMonitor.enabled`.

## Install

```sh
helm install skill-ci charts/skill-ci-controller -n skill-ci --create-namespace
kubectl -n skill-ci get skillevals
```

The chart is meant to be installed once per namespace under the release name `skill-ci`: resource names
default to the chart name (`skill-ci-controller`) and the controller hardcodes the runner ServiceAccount
`skill-eval-runner`.

### CRD handling

The `SkillEval` CRD lives in `crds/`. Helm installs it before everything else and never upgrades or deletes
it. After a schema change, apply the CRD by hand and then upgrade the release:

```sh
kubectl apply --server-side -f charts/skill-ci-controller/crds/
helm upgrade skill-ci charts/skill-ci-controller -n skill-ci
```

`crds/` is generated. Do not edit it: change `config/crd/` (generated by controller-gen) and run `make chart-crds`.

### Adopting an install made with `kubectl apply -k config/`

Helm 4 refuses to touch objects it does not own. `--take-ownership` makes it adopt them (it skips the check for
Helm ownership annotations on existing resources):

```sh
helm upgrade --install skill-ci charts/skill-ci-controller -n skill-ci --take-ownership
```

New installs and upgrades of Helm 4 releases use server-side apply by default (`--server-side=true`). Objects
previously managed by `kubectl apply` are adopted by SSA; use `--force-conflicts` if field manager conflicts show up.
The Deployment selector is only `app.kubernetes.io/name`, identical to `config/manager/deployment.yaml`, because
selectors are immutable.

### Helm 4 notes for this chart

- Chart API `v2` is the stable one. Chart API `v3` is experimental and opt-in (`HELM_EXPERIMENTAL_CHART_V3`),
  so this chart does not use it. See <https://helm.sh/docs/overview/>.
- Server-side apply is the default for new installs. Upgrades and rollbacks keep the release's previous method.
- OCI is the preferred distribution format, and charts can be installed by digest (`oci://...@sha256:...`).
- `--atomic` and `--force` are now `--rollback-on-failure` and `--force-replace`.

## Distribute as an OCI artifact

Nothing is pushed by this repository. With a registry reachable from where you run Helm (Harbor in the cluster
speaks plain HTTP, hence `--plain-http`):

```sh
helm package charts/skill-ci-controller -d /tmp/charts
helm push /tmp/charts/skill-ci-controller-0.1.0.tgz oci://harbor.harbor.svc.cluster.local/charts --plain-http
helm install skill-ci oci://harbor.harbor.svc.cluster.local/charts/skill-ci-controller --version 0.1.0 -n skill-ci --plain-http
```

This needs a Harbor project named `charts`. Install by digest with
`oci://harbor.harbor.svc.cluster.local/charts/skill-ci-controller@sha256:<digest>`.
