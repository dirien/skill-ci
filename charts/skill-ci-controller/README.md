# skill-ci-controller

Helm chart for the skill-ci controller: it receives Harbor `PUSH_ARTIFACT` webhooks, creates one
`SkillEval` per skill digest and model, runs a runner Job for each, and moves the `beta` and
`stable` tags in Harbor according to the lift policy (see `CONTRACT.md` in the repository root).

The chart replaces `kubectl apply -k config/`. Its defaults reproduce `config/manager/deployment.yaml`.

## Requirements

- Helm 4 (tested with v4.3.0). The chart is `apiVersion: v2`, so Helm 3 can install it too.
- Kubernetes 1.27 or newer.
- Created out of band, in the release namespace (the chart creates none of them by default):
  - Secret `harbor-credentials` (`username`, `password`)
  - Secret `harbor-webhook` (`token`, optional)
  - Secret `llm-keys` (`anthropic`; optional `openai`, `openai-base-url`, `nvidia`, `ollama`, `openrouter`), read by runner Jobs
  - ConfigMap `skill-ci-models` (key `models.yaml`)
- Optional: the Prometheus Operator CRDs for `serviceMonitor.enabled`.
- Optional: the Agent Sandbox extensions CRDs (`sandboxtemplates`, `sandboxwarmpools`, `sandboxclaims` in
  `extensions.agents.x-k8s.io`) for warm trial pods; without them every trial starts a bare `Sandbox`.
- Optional: Cilium (CRD `ciliumnetworkpolicies.cilium.io`) for the network modes `none` and `allowlist`;
  without it only `full` runs (see "Configuration lives in SkillCIConfig and SandboxProfile").

## Install

```sh
helm install skill-ci oci://ghcr.io/dirien/charts/skill-ci-controller --version 0.10.1 -n skill-ci --create-namespace
kubectl -n skill-ci get skillevals
```

The default images are `ghcr.io/dirien/skill-ci-controller`, `skill-ci-runner` and `skill-ci-sandbox`, all on the
chart's `appVersion`, so a chart of release X.Y.Z runs the images of X.Y.Z. They are public: there are no pull
secrets and no registry or image builder to set up. From a checkout, `helm install skill-ci charts/skill-ci-controller
--set image.tag=0.10.1 --set controller.runnerImage.tag=0.10.1 --set controller.sandboxImage.tag=0.10.1` does the same
(on the Pulumi stack `make deploy` installs the published chart, see `infra/Pulumi.yaml`). For private packages create a `docker-registry` Secret and
set `imagePullSecrets` (see below).

The chart is meant to be installed once per namespace under the release name `skill-ci`: resource names
default to the chart name (`skill-ci-controller`) and the controller hardcodes the runner ServiceAccount
`skill-eval-runner`.

### CRD handling

The `SkillEval`, `SandboxProfile` and `SkillCIConfig` CRDs live in `crds/`. Helm installs them before everything else and
never upgrades or deletes them. After a schema change or a new CRD (0.10.0 adds `SkillCIConfig`), apply the CRDs by hand
and then upgrade the release; without the `SkillCIConfig` CRD the upgrade fails with "no matches for kind SkillCIConfig":

```sh
kubectl apply --server-side -f charts/skill-ci-controller/crds/
helm upgrade skill-ci charts/skill-ci-controller -n skill-ci
```

`crds/` is generated. Do not edit it: change `config/crd/` (generated by controller-gen) and run `make chart-crds`.

### Configuration lives in SkillCIConfig and SandboxProfile

Since 0.10.0 the platform settings are not controller flags or Helm values. They live in two kinds of objects in the
controller namespace (CONTRACT.md "SkillCIConfig" and "SandboxProfile"):

- `SkillCIConfig` `default` (short name `scc`): the default SandboxProfile and the network policy (default mode,
  allowed modes, enforcement, always-allowed hosts, bundles, agent install hosts). The controller reads it whenever it
  resolves a run, so an edit applies to the next run without a restart. Objects with another name are ignored and
  say so in their `Ready` condition. An invalid edit leaves `Ready` `False` with the reason, and the controller keeps
  the last valid spec (or the built-in defaults, after a restart).
- `SandboxProfile` (short name `sbp`): image, size and warm pool of the trial sandboxes.

The chart creates `SkillCIConfig` `default` (from `config.*`) and each SandboxProfile in `sandboxProfiles` only when
the object does not exist yet: it looks it up (`lookup`) and, when nothing is there, renders it with
`helm.sh/resource-policy: keep`. From then on the object is yours, owned by kubectl or GitOps: upgrades never render
it again and never delete it, and changing `config.*` or `sandboxProfiles` later does not touch it. Edit the
objects instead:

```sh
kubectl -n skill-ci get scc default            # DEFAULT-NETWORK, ENFORCEMENT, DEFAULT-PROFILE, READY
kubectl -n skill-ci edit scc default
kubectl -n skill-ci get scc default -o jsonpath='{.status.conditions[?(@.type=="Ready")].message}'
kubectl -n skill-ci get sbp
kubectl -n skill-ci edit sbp default
```

A SandboxProfile this release created without the annotation (a pre-release build) is rendered once more from its live spec with the
annotation added, so the upgrade adopts it instead of deleting it. `helm template` and `helm lint` have no cluster,
so the objects always render there. Tools that render with `helm template` and apply the result (Argo CD) re-apply
the seed on every sync: with them set `config.create=false` and `sandboxProfiles.default.create=false` and keep
the objects in Git. `helm uninstall` leaves the objects in place.

### Adopting an install made with `kubectl apply -k config/`

Helm 4 refuses to touch objects it does not own. `--take-ownership` makes it adopt them (it skips the check for
Helm ownership annotations on existing resources):

```sh
helm upgrade --install skill-ci charts/skill-ci-controller -n skill-ci --take-ownership
```

New installs and upgrades of Helm 4 releases use server-side apply by default (`--server-side=true`). Objects
previously managed by `kubectl apply` are adopted by SSA; use `--force-conflicts` if field manager conflicts show up.
The Deployment selector is only `app.kubernetes.io/name`, identical to `config/manager/deployment.yaml`, because
selectors are immutable.

### Helm 4 notes for this chart

- Chart API `v2` is the stable one. Chart API `v3` is experimental and opt-in (`HELM_EXPERIMENTAL_CHART_V3`),
  so this chart does not use it. See <https://helm.sh/docs/overview/>.
- Server-side apply is the default for new installs. Upgrades and rollbacks keep the release's previous method.
- OCI is the preferred distribution format, and charts can be installed by digest (`oci://...@sha256:...`).
- `--atomic` and `--force` are now `--rollback-on-failure` and `--force-replace`.

## Distribute as an OCI artifact

Nothing is pushed by this repository. With a registry reachable from where you run Helm (Harbor in the cluster
speaks plain HTTP, hence `--plain-http`):

```sh
helm package charts/skill-ci-controller -d /tmp/charts
helm push /tmp/charts/skill-ci-controller-0.1.0.tgz oci://harbor.harbor.svc.cluster.local/charts --plain-http
helm install skill-ci oci://harbor.harbor.svc.cluster.local/charts/skill-ci-controller --version 0.1.0 -n skill-ci --plain-http
```

This needs a Harbor project named `charts`. Install by digest with
`oci://harbor.harbor.svc.cluster.local/charts/skill-ci-controller@sha256:<digest>`.

### OpenTelemetry (OTLP)

The controller can push its `skillci_*` metrics over OTLP, next to the `/metrics` endpoint (same names, labels and
values; see CONTRACT.md "OpenTelemetry export"). Three common targets:

```bash
# An OpenTelemetry Collector or Grafana Alloy in the cluster
--set otlp.endpoint=otel-collector.monitoring:4318 --set otlp.insecure=true

# The Prometheus OTLP receiver (Prometheus 3, or kube-prometheus-stack with
# prometheus.prometheusSpec.enableOTLPReceiver=true); then drop the ServiceMonitor, or every series is stored twice
--set otlp.endpoint=kps-kube-prometheus-stack-prometheus.monitoring:9090 \
  --set otlp.urlPath=/api/v1/otlp/v1/metrics --set otlp.insecure=true

# A vendor endpoint with an ingest key kept in a Secret
kubectl -n skill-ci create secret generic otlp-headers --from-literal=headers='x-honeycomb-team=<ingest key>'
--set otlp.endpoint=api.honeycomb.io:443 --set otlp.protocol=grpc --set otlp.headersSecret.name=otlp-headers
```

### LLM keys

The runner Job reads these keys of `llm-keys`. Only `anthropic` is required: it is the judge that scores every
run, whatever agent is under test.

| Key | Variable | Needed for |
| --- | --- | --- |
| `anthropic` | `ANTHROPIC_API_KEY` | The judge; Claude Code; OpenCode models `anthropic/<model>` |
| `openai` | `OPENAI_API_KEY` | Codex; Tier 2 embeddings |
| `openai-base-url` | `OPENAI_BASE_URL` | Codex endpoint; the runner uses `https://api.openai.com/v1` when it is missing |
| `ollama` | `OLLAMA_API_KEY` | OpenCode models `ollama-cloud/<model>` (Ollama Cloud, `https://ollama.com/v1`) |
| `openrouter` | `OPENROUTER_API_KEY` | OpenCode models `openrouter/<model>`. An API key, not a provisioning key (the runner rejects those) |
| `nvidia` | `NVIDIA_API_KEY` | OpenCode models `nvidia/<model>` (NVIDIA Build); Tier 2 embeddings when `openai` is missing |

### The statistical gate

From controller 0.5.0 (runner 0.5.1 and later send the trial scores) the gate asks for evidence instead of a fixed number.
`controller.thresholds.confidence` is the level of the confidence intervals it uses:

- A version is promoted to `stable` only when, on every required model, the lift reaches
  `controller.thresholds.promote` **and** the lower bound of the lift's confidence interval is above 0.
- A drop below the stable version by more than `controller.thresholds.regressionTolerance` is a `Regressed`
  verdict only when the interval of the difference lies entirely below 0. Otherwise the verdict is
  `Inconclusive`: the version is not promoted, stable stays, and it keeps `beta`.
- Runs from a runner without trial scores (before 0.5.1) fall back to the fixed thresholds.

A higher `confidence` (`"0.99"`) needs more evidence both to promote and to call a regression; a lower one
(`"0.90"`) needs less. The upgrade needs the new CRD fields: apply `crds/` by hand first, see "CRD handling".
Details: `CONTRACT.md`, section "Policy".

The ServiceMonitor selects the Service by `app.kubernetes.io/name: skill-ci-controller`, the same label the
ServiceMonitor already in the cluster uses. Do not enable both.
